MITRE ATT&CK Enterprise STIX 数据详解

2026-07-15
技术 网络安全
威胁情报 STIX MITRE ATT&CK

本文系统讲解 MITRE ATT&CK Enterprise STIX 2.1 数据的内容、概念、对象类型、字段结构与关联关系，并给出可运行的解析示例。

一、概述与数据来源

MITRE ATT&CK（Adversarial Tactics, Techniques, and Common Knowledge）是基于真实世界观察的全球可访问对抗战术和技术知识库，被安全社区广泛用于威胁检测、威胁狩猎、红蓝队演练和安全控制验证。

ATT&CK 框架分为三个域：

  • Enterprise：企业 IT 环境（Windows / Linux / macOS / 云 / 容器等）
  • Mobile：移动设备环境
  • ICS：工业控制系统环境

本文解析的是 Enterprise 域的 STIX 数据。

数据来源

属性 值
仓库地址 mitre-attack/attack-stix-data
文件路径 enterprise-attack/enterprise-attack.json（master 分支）
文件大小 ~53MB
STIX 版本（spec_version） 2.1
对象总数（objects） 25,843
对象类型数（distinct type） 16
关系对象数（relationship） 21,025

数据用途：作为机器可读的”单一事实源”，供安全产品（SIEM、EDR、威胁情报平台）导入、检索与可视化，也适合用脚本批量提取（如生成中文对照表、构建攻击图谱）。

二、STIX 2.1 核心概念

STIX（Structured Threat Information Expression）是一种结构化网络威胁情报表达标准，采用 JSON 格式。STIX 2.1 用两类对象描述威胁信息：

概念 全称 说明
SDO STIX Domain Object（域对象） 描述”事物”本身，如攻击模式（attack-pattern）、恶意软件（malware）、威胁组织（intrusion-set）、身份（identity）等
SRO STIX Relationship Object（关系对象） 描述”事物之间的联系”，即 relationship 类型，用 source_ref / target_ref 指向两个对象的 ID

2.1 公共属性

几乎每个对象都带如下公共字段：

字段 说明
type 对象类型，如 attack-pattern、relationship
spec_version STIX 规范版本，通常为 2.1
id STIX ID，形如 attack-pattern--<UUID>；全局唯一
created / modified 创建/修改时间（ISO 8601）
created_by_ref 创建者引用，通常指向一个 identity 对象
object_marking_refs 标记引用数组，指向 marking-definition（如 TLP 分级）
external_references 外部引用数组；ATT&CK 通过它挂载官方 ID 与网址
x_mitre_* 前缀字段 ATT&CK 对 STIX 的专有扩展字段
revoked 布尔；为 true 表示该对象已被新版本取代
x_mitre_deprecated 布尔；为 true 表示该对象已弃用

2.3 marking-definition 与 identity

  • marking-definition（本文件 1 个）：描述数据标记，最常见的是 TLP（Traffic Light Protocol） 分级，控制信息的共享范围（如 WHITE / GREEN / AMBER / RED）。
  • identity（本文件 1 个）：描述数据归属方。本文件中即 MITRE 自身，通过 created_by_ref 关联到各对象，表示”这条 ATT&CK 条目由 MITRE 发布”。

2.4 x-mitre-* 自定义扩展字段

ATT&CK 在标准 STIX 基础上增加了 x-mitre-* 前缀的自定义字段，常见的有：

字段 说明
x_mitre_shortname 战术短名称（小写），用于技术-战术关联
x_mitre_platforms 适用平台列表
x_mitre_domains 所属域（如 enterprise-attack）
x_mitre_is_subtechnique 是否为子技术
x_mitre_data_sources 可检测该技术的数据源
x_mitre_deprecated 是否已弃用

x_mitre_shortname 短名（小写），如 execution；是技术↔战术的关联键
external_references[].external_id 战术编号 TAxxxx
description 该阶段的目标描述

3.3 矩阵（Matrix）— x-mitre-matrix

x-mitre-matrix 只有 1 个，它用 tactic_refs（战术 ID 数组）声明 Enterprise 矩阵的战术从左到右的排列顺序，是构建可视化矩阵的骨架。

tactic_refs 数组的顺序即 ATT&CK 官网上矩阵从左到右的战术列顺序。解析时应以 tactic_refs 而非 external_id 的数字大小来决定战术排列。

3.4 威胁组织（Intrusion Set）— intrusion-set

威胁组织（也称为 APT 组织、威胁团伙）代表已知的威胁行为者，是具有共同归因的一组恶意活动。

关键字段 说明
name 组织名称（MITRE 命名，如 APT28）
aliases 别名列表（厂商命名、公开名称等）
description 组织背景、活动时间、目标行业等

本文件活跃入侵组织 174 个（含弃用共 189 个），包括知名的 APT28、APT29、Lazarus Group、FIN7 等。

组织通过 uses 关系关联使用的技术和软件，通过 attributed-to 关系关联战役。

3.5 软件（Software）— malware + tool

软件分为两类：

类型 STIX type 活跃数量 说明
恶意软件 malware 726 RAT、木马、勒索软件、后门等（含弃用共 729）
工具 tool 95 合法工具被攻击者滥用（PsExec、Mimikatz 等）
合计 821

注：Mimikatz 在 ATT&CK 中归类为 Tool（工具），不是 Malware。

软件对象关键字段：

字段 说明
is_family 是否为恶意软件家族（布尔值）
x_mitre_platforms 支持平台
x_mitre_aliases 别名

软件通过 uses 关系关联到使用的技术。

3.6 战役（Campaign）— campaign

战役是一组在特定时间窗口内针对特定目标发生的、具有共同归因的恶意活动。

  • 活跃数量：56 个
  • 有明确的时间范围（first_seen、last_seen）
  • 通过 attributed-to 关系归属到组织
  • 通过 uses 关系关联使用的技术和软件

3.7 缓解措施（Course of Action）— course-of-action

缓解措施代表可以防止技术成功执行的安全配置、最佳实践或工具。

  • 活跃数量：44 个（含弃用共 268 个）
  • 通过 mitigates 关系关联到对应的技术

3.8 数据源体系（Data Source / Data Component）

数据源代表可用于检测行为的信息来源，数据组件是数据源下的具体事件类型。

类型 ID 前缀 数量 说明
Data Source DSxxxx 38 如 Process、File、Network、Registry 等
Data Component 无单独 ID 109 如 Process Creation、File Modification 等

数据组件是技术 x_mitre_data_sources 字段实际引用的单位，通过 detects 关系关联到技术。

主要数据源分类：

  • 进程相关：Process Creation、Process Termination、Process Access
  • 文件相关：File Creation、File Modification、File Deletion
  • 网络相关：Network Connection、Network Traffic、DNS Query
  • 注册表相关：Registry Key Creation、Registry Value Modification
  • 认证相关：Logon Session、Authentication Event
  • 命令行相关：Command Execution、Script Execution

3.9 分析与检测（Analytic / Detection Strategy / Collection）

类型 数量 说明
x-mitre-analytic 1,758 具体的检测分析逻辑（如 Sigma 规则片段）
x-mitre-detection-strategy 699 检测策略，通过 detects 关系指向被检测的技术
x-mitre-collection 1 数据集合元信息

检测对象描述了如何利用数据源检测特定技术，包含检测逻辑、所需数据源、误报说明和检测置信度等。

四、对象间关联关系（SRO）

ATT&CK 的知识价值很大程度来自对象之间的 relationship。

4.1 核心关系类型

relationship_type 含义 source（起点） target（终点） 数量
uses 采用 组织/软件/战役 技术/子技术/软件 18,220

attributed-to 归属 战役 威胁组织 26

4.2 关系方向与知识图谱

关系是有方向的，source_ref（源）和 target_ref（目标）不要搞反。通过关系可以构建完整的攻击知识图谱：

4.3 三种核心导航路径

  1. 技术 ↔ 战术：技术对象内 kill_chain_phases[].phase_name 与战术的 x_mitre_shortname 对应，无需经过 relationship
  2. 子技术 ↔ 父技术：通过 subtechnique-of 关系（source=子技术，target=父技术）
  3. 组织/软件 → 技术：通过 uses 关系

4.4 典型查询路径

查询场景 关系路径
某组织使用的技术 intrusion-set --uses--> attack-pattern
某技术的检测方法 detection-strategy --detects--> attack-pattern
某技术的缓解措施 course-of-action --mitigates--> attack-pattern
某恶意软件使用的技术 malware --uses--> attack-pattern
某技术的子技术 sub_attack-pattern --subtechnique-of--> parent_attack-pattern

5.4 ATT&CK 矩阵可视化原理

ATT&CK 矩阵是一个二维表格：

  • 列：战术（按 x-mitre-matrix 的 tactic_refs 顺序排列）
  • 行：技术
  • 单元格：属于该战术的技术

构建步骤：

  1. 获取 x-mitre-matrix 对象的 tactic_refs 数组，确定战术列顺序
  2. 对每个技术，根据 kill_chain_phases 中的 phase_name 分配到对应战术列
  3. 子技术显示在父技术下方（缩进）
  4. 已废弃/已撤销的对象不显示

6.4 常见坑

  1. 务必过滤 revoked / x_mitre_deprecated：否则统计数字虚高（如原始 attack-pattern 858 个，过滤后仅 697 个有效）
  2. STIX 版本是 2.1 不是 2.0：enterprise-attack.json 的 spec_version 为 2.1
  3. 版本间改名/新增：如 defense-evasion → stealth、新增 TA0112 Defense Impairment。不要硬编码战术名称或编号映射
  4. 关系方向：source_ref 和 target_ref 有方向，不要搞反（如 uses 的 source 是组织/软件，target 是技术）
  5. 多战术归属：一个技术可能属于多个战术（kill_chain_phases 是数组），不要假设一对一关系
  6. 子技术平台可不同：子技术会继承父技术的一些属性，但平台等字段可能与父技术不同
  7. 官方数据无中文：STIX 导出仅含英文，中文翻译需依赖社区资源（如 seccmd/Attack_CN 项目）
  8. HTML 清理：description 字段包含 HTML 标签，展示前需要清理

这篇文章用 C2（Command & Control）的架构思维来设计 Agent 通信：用 A2A 协议做标准化通信，用 STIX 2.1 做情报交换格式，用 ATT&CK 技术 ID 做攻防动作的统一语义。不依赖任何框架，从概念到实战一次讲透。

三、C2 思维与 Agent 通信的映射

3.1 核心类比

本文不实现真正的 C2 框架，而是用 C2 的架构思维来设计 Agent 通信：

C2 概念 Agent 通信对应 说明
Operator（操作员） 紫队 Agent 下达指令、监控全局、拥有否决权
Beacon（信标） 红队 / 蓝队 Agent 定期汇报状态、接收和执行指令
C2 Channel（通道） A2A Task + JSON-RPC 指令和数据的传输通道

3.2 三条设计原则

原则一：紫队 = Operator，红蓝队 = Beacon

红蓝队 Agent 不是完全自主的——它们定期向紫队同步 Task 状态（类比 Beacon 的 Callback），紫队拥有否决权和终止权。

原则二：所有情报用 STIX 2.1 封装

不管是红队的攻击成果还是蓝队的告警事件，全部封装成 STIX 2.1 对象后通过 A2A Artifact 传输。格式统一，便于自动化分析。

原则三：攻防动作用 ATT&CK ID 标识

Agent 之间不说”我扫了端口”，而说”我执行了 T1595”。语义统一，紫队 Agent 可以自动关联红队进度和蓝队告警。

架构约束：蓝队 Agent 禁止直接向红队 Agent 发送 Stop 指令。所有阻断、暂停、终止动作必须通过紫队 Agent 编排下发——这保证了”紫队是唯一编排者”的架构安全性，避免红蓝队越权通信。

3.3 Subagent-Driven Development：子 Agent 执行

Plan 确认后，AI 对每个任务启动一个独立的子 Agent 来执行。每个子 Agent：

什么时候不适合用这套流程

这套流程虽然强大，但并非万能：

  • 算法竞赛/面试题：AI 可能给出复杂度过高的解，需要人工判断
  • 安全关键系统（医疗、金融核心）：必须人工主导，AI 辅助而非替代
  • 遗留代码大规模重构：上下文太大，AI 容易理解偏差，需分阶段推进
  • 探索性原型：严格 Spec 会束缚创造力，先用 Vibe Coding 快速验证，确定方向后再走流程

四、实战：构建一个代码审计 Agent

代码审计（Code Audit）是系统化地对源代码进行安全漏洞检测、合规性检查、风险分析的过程。它不同于代码审查（Code Review）——审计是”专项安全体检”，审查是”日常健康检查”。

4.1 代码审计是什么

维度 代码审计（Code Audit） 代码审查（Code Review）
执行者 专业安全团队/自动化工具 同侪开发者
时间点 上线前/定期专项 每次 PR/合并
深度 系统性、全面性 增量式、聚焦变更
标准 OWASP/CWE/合规标准 团队编码规范
输出 正式审计报告 Review Comments

核心目标：

  1. 发现安全漏洞：SQL 注入、XSS、命令注入、越权访问、反序列化漏洞等
  2. 确保合规性：检查是否满足等保 2.0、GDPR、SOC2、PCI-DSS 等合规要求
  3. 降低安全风险：在代码上线前识别并修复安全隐患
  4. 建立安全基线：沉淀安全模式，形成团队可复用的安全编码规范

4.2 代码审计的工作内容

一次完整的代码审计覆盖 七大维度：

维度 检查要点 常见漏洞
注入漏洞 用户输入是否直接拼接到 SQL/命令/路径中？ SQL 注入、命令注入、LDAP 注入
认证授权 认证逻辑是否有绕过风险？权限校验是否完整？ 越权访问、会话固定、JWT 伪造
敏感数据 密码、密钥、Token 是否硬编码？日志中是否打印了敏感信息？ 硬编码凭据、日志泄露、明文存储
加密安全 是否使用过时算法（MD5/SHA1/DES）？密钥是否硬编码？ 弱加密算法、不安全随机数
依赖安全 第三方库是否存在已知 CVE？是否使用已停止维护的库？ 供应链攻击、已知漏洞利用
配置安全 调试模式是否关闭？CORS 是否过于宽松？ 信息泄露、Debug 端点暴露
日志安全 是否记录了安全操作？日志是否包含敏感信息？ 日志注入、操作不可追溯

4.3 为什么用 Agent 做代码审计

人工审计的三大瓶颈：

瓶颈 具体表现 量化影响
效率低下 一个安全工程师一天只能审计 500-1000 行代码 中型项目（5 万行）需要 2-3 人月
知识盲区 单个工程师不可能精通所有语言、所有漏洞类型 熟悉的领域容易发现，陌生的容易漏掉
一致性差 不同审计人员标准不一，精力状态波动导致覆盖率不稳定 周二和周五的审计结果可能差异巨大

Agent 的五大优势：

优势 说明
理解上下文 不只是模式匹配——能理解代码的业务逻辑
多维度并行 多个子 Agent 同时从注入、认证、加密等维度并行审计
知识持续更新 通过 Skill 机制，随时加载最新的漏洞模式
生成可执行修复 不仅指出问题，还能生成具体的修复代码
自适应学习 对同一项目的重复审计，Agent 能记住项目特有的安全模式

关键原则：Agent 负责”发现”和”建议”，人负责”判断”和”决策”。严重漏洞必须经过人工确认（HITL）。

Agent 开发主流技术路线

2026-06-29
技术 AI
MCP Agent开发 Skills 上下文工程

2024 年，Agent 开发是这样的：一个巨大的 System Prompt，几百行，塞满了 You are an expert...、If...then...。改一个字，整个 Agent 就跑偏了。

2026 年，Agent 开发走向了解耦：Prompt 被拆成 Skills（怎么做）和 Rules（不能做）；接口被标准化为 MCP；编排分化出两条路径——写代码深度定制，或拖拽配置快速上线。

路径 A：代码/框架驱动（工程化）——用 LangGraph / CrewAI / AutoGen 写代码，深度定制复杂业务逻辑，适合生产级部署。
路径 B：配置/平台驱动（产品化）——用 Dify / Coze / Flowise 可视化编排，Skills + MCP + Rules 组合配置，适合快速原型和标准化场景。

两条路径共享同一套底层公式：

Agent 开发 = 能力定义（Skills/MCP）+ 行为约束（Rules）+ 推理引擎（LLM）+ 编排载体（框架/平台/代码）

这篇文章按公式逐层拆解：每一层是什么、两条路径各怎么做、2026 年主流工具怎么选。

一、核心公式与两条路径

1.1 统一公式拆解

这四个组件缺一不可：能力定义决定了 Agent 的操作范围，行为约束划定了安全边界，推理引擎提供智力支撑，编排载体负责把一切串起来跑。

1.2 路径 A vs 路径 B

维度 路径 A：代码/框架驱动 路径 B：配置/平台驱动
开发方式 选框架 → 写代码（LangGraph/CrewAI/AutoGen） 组合 Skills + MCP + Rules（Dify/Coze/Flowise）
能力定义 框架内置 Tool + 可选 MCP 统一 MCP 协议，即插即用
行为约束 代码中实现安全检查 平台内置 Rules + Hooks
推理引擎 自由切换模型，代码控制 平台内置模型路由
编排载体 代码定义 Agent Loop + 多 Agent 协作 可视化 Workflow + 标准化编排模式
适合人群 开发者、工程师 开发者 + 业务人员 + 产品经理
核心优势 深度定制、复杂逻辑、完全掌控 快速原型、低门槛、开箱即用

一句话总结：路径 A 是”造轮子”——完全掌控，适合深度定制；路径 B 是”拼乐高”——快速搭建，适合标准化场景。两条路径在 2026 年都已成熟，选哪条取决于你的场景，而不是你的”段位”。

二、能力定义：Skills 与 MCP

核心观点：能力定义层决定了 Agent 的”手”能伸多远——Skills 定义它懂什么流程，MCP 定义它能接什么系统。

2.1 Skills：Markdown 即技能包

Skills 是存放在 SKILL.md 中的 Markdown 指令包，教 Agent 如何完成特定任务。它把”每次手写 Prompt”变成了”菜谱式复用”。Skills 的本质是让传统的 System Prompt 走向结构化、模块化——在 IDE 中它表现为 .cursor/rules/ 下的配置文件或 AGENTS.md，在平台上表现为封装好的技能包。

维度 说明
存放位置 路径 A：项目级 .cursor/skills/ 或 .claude/skills/；路径 B：平台内置 Skill 市场
触发方式 自动匹配（根据用户意图）或手动 /skill-name
生态现状 2026 年已有数千个社区 Skills，覆盖 TDD、代码审查、文档生成、部署等
路径差异 路径 A 中 Skills 增强代码可控性；路径 B 中 Skills 是开发的核心载体

2.2 MCP：AI 界的 USB-C

MCP（Model Context Protocol）是 Anthropic 推出的开放协议，让 AI 应用通过统一接口连接外部工具和数据源。一个 MCP Server 写一次，所有支持 MCP 的 AI 应用都能用——解决了 M×N 集成地狱。

维度 2026 年现状
生态规模 2000+ 公共 MCP Server，覆盖数据库、云 API、监控、CI/CD

协议演进 支持 HTTP streamable transport，不再局限于 stdio
行业地位 Anthropic + OpenAI + Google + Microsoft 全部支持

2.3 Computer Use：无 API 系统的最后拼图

Tool Calling 解决了”有 API 的系统”，MCP 统一了接口标准，Computer Use 解决了”没有 API 的遗留系统”——AI 直接看屏幕、点鼠标、敲键盘。目前适用场景有限，但填补了关键空白。

三、行为约束：Rules 与 Hooks

核心观点：能力定义让 Agent “能做事”，行为约束让 Agent “不乱来”——这是从 Demo 到生产最关键的一步。

3.1 Rules：持久化的项目约定

Rules 是每次对话自动注入的项目级指令，约束 Agent 的行为边界。路径 A 放在 .cursor/rules/ 或项目根目录的 AGENTS.md 中；路径 B 在平台设置中配置。

3.2 Hooks：自动化安全网

Hooks 在 Agent 执行工具前后触发，用于校验、审计或自动化拦截。路径 A 通过配置文件定义，路径 B 通常内置在平台中。

3.3 三者协同

为什么这很重要？ 因为 Skills + Rules + Hooks 解决了 Agent 开发中最核心的痛点：可复用性和可预测性。你不再需要每次对话都重复解释”我们怎么做 TDD”，你只需要写一次 Skill，永久生效。

核心观点：2026 年的模型已经足够强，瓶颈不在模型能力，而在”喂给模型的信息质量”。

4.2 上下文工程三原则

上下文工程（Context Engineering）是 2026 年 Agent 开发的核心技能，比 Prompt Engineering 更关键：

  2. 分层注入：System Prompt → Skills → Rules → 对话历史 → 工具输出，按优先级分层
  3. 动态裁剪：根据当前任务自动选择注入哪些 Skills，不是全部加载

六、Harness Engineering：生产就绪的七个维度

核心观点：Agent 循环本身只占 5% 的代码，剩下 95% 全在解决”循环跑起来之后怎么保证不跑偏”。这就是 Harness Engineering 的价值。

行业数据显示，大约 80%-90% 的 AI Agent 项目没能进入生产环境——不是因为 AI 不够聪明，而是因为没有人搭好它”干活的环境”。Harness Engineering 就是解决这个问题的。

领域 核心问题 2026 年最佳实践 路径 A 做法 路径 B 做法
权限控制 Agent 会不会 rm -rf？ 7 层纵深防御 + Deny-First 自建权限层 平台内置
上下文管理 对话长了就失忆？ 5 层压缩流水线 + 自动总结 自建 Memory 平台内置
工具调度 并发调用安全吗？ 并发感知执行器，互斥串行 代码控制 平台调度
错误恢复 工具调用失败怎么办？ 自动重试 + 自我修正 + 熔断 自建重试逻辑 平台内置
成本控制 一次对话花了多少钱？ Token 预算 + 实时追踪 + 告警 自建监控 平台仪表盘
可观测性 Agent 内部发生了什么？ OpenTelemetry + 调用链追踪 自建 Trace 平台内置
人工介入 关键操作谁确认？ Human-in-the-loop + 审批策略 自建审批流 平台内置

黄金法则：永远不要让 Agent 在没有人类确认的情况下，直接向客户发送邮件或操作真实钱包。无论是路径 A 的代码 interrupt 机制，还是路径 B 平台的审批节点，人类作为最后一道防线是 2026 年商业化落地的硬性要求。

关键认知：路径 A 在 Harness 上投入更大，但换来完全掌控；路径 B 开箱即用，但定制空间有限。这是两条路径最核心的 trade-off。

一、Agent 相关概念简介

（一）基础：Token 与 Context Window

在聊所有高级概念之前，先搞清楚 AI 最底层的两个限制——它们决定了 AI 能”想”多少。

1.1 Token — 文字的最小单元

维度 说明
定义 LLM 处理文本的最小计量与计费单位，不等于”一个单词”
换算 英文约 4 字符 ≈ 1 Token；中文约 1~2 字 ≈ 1 Token
影响 API 费用、速率限制、max_tokens 上限都以 Token 计算

一句话：Token 是 AI 世界的”最小货币单位”——你跟 AI 的每一次交流，最终都变成 Token 在账单上累积。

1.2 Context Window — 单次处理的”记忆上限”

维度 说明
定义 模型单次对话能”看到”的最大 Token 数量（文字+代码+工具输出总和）
容量 200K Token ≈ 15 万中文字 ≈ 一本中等篇幅的书
瓶颈 对话轮次多了、文件读多了，窗口会满——满了就失忆或报错
解决方案 上下文压缩（Compaction）：把早期历史总结成摘要，腾出空间继续工作

各模型上下文窗口容量差异很大：GPT-4o 为 128K，Claude 为 200K，Gemini 2.0 已达 2M Token。选模型时，上下文窗口大小是关键指标之一。

Compaction 的工程智慧：Claude Code 实现了 5 层压缩流水线——从零成本的”裁剪无关历史”到”让 LLM 把整个历史总结成结构化 Markdown 快照”，先用便宜的本地操作，实在不行再花 API 钱做重写总结。

关系：Token 是”最小单元”，Context Window 是”单次容量上限”。

（二）指令：Prompt 与 Context Engineering

有了基础能力，下一步是”让 AI 理解你到底要它干什么”。

2.1 Prompt — 指令话术

维度 说明
定义 发给 LLM 的输入文本，告诉它”你是谁、做什么、按什么格式回答”
三层结构 System Prompt（角色定义+全局规则）+ User Prompt（具体任务）+ Assistant 历史回复
本质 Prompt 就是你给 AI 的”工作说明书”

你打开 Claude Code，说”帮我修一下这个 Bug”。这一句话是 Prompt。但背后系统自动拼进去了：你是谁、项目的技术栈、有哪些可用工具、安全规则约束……这些都是 Prompt 的一部分。

2.2 Context Engineering — 信息流管控

维度 说明
定义 有意识地设计 Agent 每一轮能看到什么信息——系统提示、规则、文件、工具输出、记忆
为什么重要 好的上下文工程比换更强的模型更能提升 Agent 表现
公式 上下文工程 = 精选信息 + 组织结构 + 动态裁剪
类比 给 AI 递”精准小抄”，而不是把整本书扔过去

关系：Prompt 是”一句话指令”，Context Engineering 是”你给 AI 看的全部资料的编排策略”。从 Prompt Engineering 到 Context Engineering，是从”写提示词”到”管控信息流”的范式升级。

（三）查证：RAG 与向量数据库

AI 最致命的问题——幻觉（Hallucination）。你问它”公司上个季度销售额是多少”，它不知道，但会编一个数字，而且编得理直气壮。解决方案：让它先查资料再回答。

3.1 RAG — 检索增强生成

维度 说明
定义 在 AI 回答之前，先从外部知识库检索相关文档，作为参考资料塞进 Prompt，再生成答案
三步流程 检索（Retrieval）→ 增强（Augmented，把文档拼进 Prompt）→ 生成（Generation）
解决的问题 LLM 知识过时 + 不知道你的私有资料 → 按文档回答，不瞎编
典型场景 企业知识库问答、智能客服、合同审查

你把公司 200 页的员工手册做成 RAG 知识库。问”年假有多少天”，系统先检索到《员工手册》相关段落，拼进 Prompt 变成”根据以下上下文回答：……Question: 年假有多少天？”——回答就基于真实文档，而不是模型瞎猜。

RAG 的前提是知识库本身质量过硬——“垃圾进，垃圾出”。如果检索到的文档本身就是错的，AI 依然会按照错误文档回答。RAG 解决了”不知道”的问题，但没解决”推理”的问题。

3.2 向量数据库 — RAG 的检索引擎

传统关键词搜索有硬伤：”销售额”搜不到”营收”，”怎么做红烧肉”匹配不到”如何烹饪红烧肉”。

维度 说明
定义 专门存储和检索 Embedding 向量的数据库，支持”语义相似度搜索”
核心原理 把文本转成向量（Embedding）→ 语义相近的内容向量距离近 → 搜”红烧肉”也能找到”红烧排骨”
检索流程 文档切块(Chunking) → 向量化存入 → 用户提问向量化 → 相似度检索 Top-K 片段 → 拼进 Prompt
代表产品 Milvus、PGVector、Chroma、Pinecone

关系：RAG 是”方法论”（让 AI 查资料再回答），向量数据库是”核心引擎”（怎么查）。没有向量数据库，RAG 只能做关键词匹配，效果大打折扣。

（四）行动：Tool Calling、MCP 与 Computer Use

LLM 本质是文字处理器——只输出文字，不能操作文件、不能调 API、不能上网。让 AI 真正”做事”需要三层能力。

4.1 Tool Calling — 函数调用

维度 说明
定义 LLM 返回结构化 JSON 表达”我要调某某工具，参数是这些”，外层程序执行并反馈结果
本质 模型只负责”做决定”（选哪个工具+传什么参数），程序负责”真执行”
一个循环 用户问”上海天气”→ 模型返回 get_weather(location="ShangHai") → 程序调天气 API → 结果还给模型 → 模型用自然语言回答你

LLM 说”我要读文件”，Agent 帮它读。LLM 说”我要调 API”，Agent 帮它调。LLM 自己什么都没做，但它决定了每一步该做什么。

4.2 MCP — 模型上下文协议

最早的实现方式是把每个工具的集成逻辑硬编码在 Agent 主程序里。这导致了著名的 M×N 集成地狱：N 个 AI 模型 × M 个外部工具 = N×M 套定制集成。

维度 说明
定义 Anthropic 2024年11月开源的开放标准协议，让 AI 应用通过统一接口连接外部工具和数据源
三个角色 Host（AI 应用，如 Claude Desktop）→ Client（协议组件，1:1 连接 Server）→ Server（把外部系统能力包装成标准化工具）
三种能力 Tools（可执行操作）、Resources（只读数据）、Prompts（提示模板）
行业地位 2025 年 12 月捐赠给 Linux 基金会 Agentic AI Foundation，OpenAI、Block 等公司随后宣布支持，月下载量 9700 万次

就像 USB-C 统一了充电口——MCP 统一了 AI 工具接口。你不需要为每个模型单独写集成代码，只要实现一个 MCP Server，所有支持 MCP 的 AI 应用都能用。

4.3 Computer Use — 像人一样操作电脑

维度 说明
定义 AI 通过虚拟鼠标和键盘，直接操控电脑屏幕上的应用——打开软件、点击按钮、填写表单
与 Tool Calling 的区别 Tool Calling 是”调 API”（结构化、精确），Computer Use 是”看屏幕+操作 GUI”（视觉驱动、通用）
代表产品 Anthropic Claude Computer Use、OpenAI CUA（Computer Using Agent）
典型场景 操作没有 API 的遗留系统、跨多个应用完成复杂流程

（五）沉淀：Skill 技能包

5.1 Skill — 技能包

维度 说明
定义 存放在 SKILL.md 中的 Markdown 指令包，教 Agent 如何完成特定任务
与 Prompt 的区别 Prompt 是”一次性指令”，Skill 是”可复用的流程级指令包”——每次遇到同类任务自动加载
存放位置 项目级 .cursor/skills/ 或个人级 ~/.cursor/skills/
典型场景 PR 审查规范、生成 commit message、处理 PDF 合并、代码审查清单

关系：Prompt 是”每次口头教做菜”，Skill 是”写成菜谱贴在厨房”——下次说”做红烧肉”，Agent 自动按菜谱来，不用从头教。

（六）自主：Agent 智能体

6.1 Agent — 智能体

维度 说明
核心公式 Agent = Model（智力）+ Harness（手脚+流程）
核心循环 观察 → 规划 → 行动 → 验证 → 重复，直到任务完成
与 LLM 的区别 LLM 是”一问一答的文字处理器”；Agent 是”能自己拆任务、调工具、看结果、再调整的自主系统”

一句话道破本质：Agent 就是所有不需要智能的部分拼在一起，给真正智能的 LLM 打工。 LLM 不会读文件？Agent 帮它读。LLM 不会联网？Agent 帮它搜。LLM 不会执行命令？Agent 帮它跑。

（七）落地：Harness、Workflow 与 Workspace Agent

前面的概念让 AI 能”做事”，但要让它在生产环境中可靠运行，还需要三层保障。

7.1 Harness — 执行框架 / 安全外壳

维度 说明
定义 包裹在 LLM 外面的整套软件基础设施，负责 Agent 循环、工具调用、上下文组装、权限审批和用户界面
三大职责 ① 权限控制（7 层纵深防御）② 上下文管理（自动压缩、裁剪、注入）③ 工具调度（并发安全、流式执行）

Harness 的安全哲学：

原则 含义
否决优先（Deny-First） 宁可错误阻止一个安全操作，绝不错误放行一个危险操作
渐进信任（Graduated Trust） 每次新会话，信任从零开始重建——Agent 一开始什么都不能做
纵深防御（Defense in Depth） 7 层独立防线，任何一层都能拦截——从全局禁止列表到高风险显式确认

Harness 是”把 LLM 包装成可靠 Agent”的系统工程。Claude Code 的源码中，核心 Agent 循环只占 5%，剩下 95% 全在解决”循环跑起来之后怎么保证不跑偏”。

7.2 Workflow — 工作流

维度 说明
定义 把多步骤任务编排成可重复、有顺序的流程
与 Agent 的区别 Agent 是”自主从零规划每一步”；Workflow 是”步骤和分支相对固定，但每步可调用 LLM/工具”
典型场景 文档更新：提案 → 人工 Review → 按任务清单实施 → 跑 CI → 归档

Workflow 是”标准化流水线”——你知道要做什么，只是用 AI 来加速每一步。Agent 是”自主探索”——你不知道具体怎么走，但告诉 AI 目标，让它自己找路。

7.3 Workspace Agent — 长期数字员工

维度 说明
定义 能持续运行、跨会话保持上下文、拥有持久记忆和工作空间的 Agent
与普通 Agent 的区别 普通 Agent 是”一次性临时工”（会话结束就失忆）；Workspace Agent 是”长期员工”（记住你的偏好、项目上下文、历史决策）
代表 OpenAI Workspace Agents、团队共享智能体
关键能力 持久记忆 + 权限体系 + 团队协作 + 持续学习

（八）总结

一句话总结：AI 的进化，就是从”给你一段文字”到”帮你把事办成”的旅程。Token 和 Context Window 是基础限制，Prompt 和 Context Engineering 让 AI 听懂你，RAG 让 AI 不再瞎编，Tool Calling / MCP / Computer Use 给 AI 装上了手脚，Skill 沉淀了重复流程，Agent 让 AI 能自主执行，Harness / Workflow / Workspace Agent 让它能安全、可靠、持续地落地干活。

Agent 概念快速入门

2026-06-25
技术 AI
Agent Token Prompt RAG MCP Tool Calling Skill Workflow

两年前，我们惊叹于 ChatGPT 能聊天。今天，AI 已经能自己读文件、调 API、操作电脑、自主拆任务执行——它不是”更会聊了”，而是”进化出了手脚”。

这篇文章带你理清这背后每一个关键概念：从最底层的 Token 和 Context Window，到让 AI 查资料再回答的 RAG，再到统一工具接口的 MCP、沉淀工作流程的 Skill，最后到能自主落地干活的 Agent 和 Harness。

一、基础：Token 与 Context Window

在聊所有高级概念之前，先搞清楚 AI 最底层的两个限制——它们决定了 AI 能”想”多少。

1.1 Token — 文字的最小单元

维度 说明
定义 LLM 处理文本的最小计量与计费单位，不等于”一个单词”
换算 英文约 4 字符 ≈ 1 Token；中文约 1~2 字 ≈ 1 Token
影响 API 费用、速率限制、max_tokens 上限都以 Token 计算

一句话：Token 是 AI 世界的”最小货币单位”——你跟 AI 的每一次交流，最终都变成 Token 在账单上累积。

1.2 Context Window — 单次处理的”记忆上限”

维度 说明
定义 模型单次对话能”看到”的最大 Token 数量（文字+代码+工具输出总和）
容量 200K Token ≈ 15 万中文字 ≈ 一本中等篇幅的书
瓶颈 对话轮次多了、文件读多了，窗口会满——满了就失忆或报错
解决方案 上下文压缩（Compaction）：把早期历史总结成摘要，腾出空间继续工作

各模型上下文窗口容量差异很大：GPT-4o 为 128K，Claude 为 200K，Gemini 2.0 已达 2M Token。选模型时，上下文窗口大小是关键指标之一。

Compaction 的工程智慧：Claude Code 实现了 5 层压缩流水线——从零成本的”裁剪无关历史”到”让 LLM 把整个历史总结成结构化 Markdown 快照”，先用便宜的本地操作，实在不行再花 API 钱做重写总结。

关系：Token 是”最小单元”，Context Window 是”单次容量上限”。

二、指令：Prompt 与 Context Engineering

有了基础能力，下一步是”让 AI 理解你到底要它干什么”。

2.1 Prompt — 指令话术

维度 说明
定义 发给 LLM 的输入文本，告诉它”你是谁、做什么、按什么格式回答”
三层结构 System Prompt（角色定义+全局规则）+ User Prompt（具体任务）+ Assistant 历史回复
本质 Prompt 就是你给 AI 的”工作说明书”

你打开 Claude Code，说”帮我修一下这个 Bug”。这一句话是 Prompt。但背后系统自动拼进去了：你是谁、项目的技术栈、有哪些可用工具、安全规则约束……这些都是 Prompt 的一部分。

2.2 Context Engineering — 信息流管控

维度 说明
定义 有意识地设计 Agent 每一轮能看到什么信息——系统提示、规则、文件、工具输出、记忆
为什么重要 好的上下文工程比换更强的模型更能提升 Agent 表现
公式 上下文工程 = 精选信息 + 组织结构 + 动态裁剪
类比 给 AI 递”精准小抄”，而不是把整本书扔过去

关系：Prompt 是”一句话指令”，Context Engineering 是”你给 AI 看的全部资料的编排策略”。从 Prompt Engineering 到 Context Engineering，是从”写提示词”到”管控信息流”的范式升级。

三、查证：RAG 与向量数据库

AI 最致命的问题——幻觉（Hallucination）。你问它”公司上个季度销售额是多少”，它不知道，但会编一个数字，而且编得理直气壮。解决方案：让它先查资料再回答。

3.1 RAG — 检索增强生成

维度 说明
定义 在 AI 回答之前，先从外部知识库检索相关文档，作为参考资料塞进 Prompt，再生成答案
三步流程 检索（Retrieval）→ 增强（Augmented，把文档拼进 Prompt）→ 生成（Generation）
解决的问题 LLM 知识过时 + 不知道你的私有资料 → 按文档回答，不瞎编
典型场景 企业知识库问答、智能客服、合同审查

你把公司 200 页的员工手册做成 RAG 知识库。问”年假有多少天”，系统先检索到《员工手册》相关段落，拼进 Prompt 变成”根据以下上下文回答：……Question: 年假有多少天？”——回答就基于真实文档，而不是模型瞎猜。

RAG 的前提是知识库本身质量过硬——“垃圾进，垃圾出”。如果检索到的文档本身就是错的，AI 依然会按照错误文档回答。RAG 解决了”不知道”的问题，但没解决”推理”的问题。

3.2 向量数据库 — RAG 的检索引擎

传统关键词搜索有硬伤：”销售额”搜不到”营收”，”怎么做红烧肉”匹配不到”如何烹饪红烧肉”。

维度 说明
定义 专门存储和检索 Embedding 向量的数据库，支持”语义相似度搜索”
核心原理 把文本转成向量（Embedding）→ 语义相近的内容向量距离近 → 搜”红烧肉”也能找到”红烧排骨”
检索流程 文档切块(Chunking) → 向量化存入 → 用户提问向量化 → 相似度检索 Top-K 片段 → 拼进 Prompt
代表产品 Milvus、PGVector、Chroma、Pinecone

关系：RAG 是”方法论”（让 AI 查资料再回答），向量数据库是”核心引擎”（怎么查）。没有向量数据库，RAG 只能做关键词匹配，效果大打折扣。

四、行动：Tool Calling、MCP 与 Computer Use

LLM 本质是文字处理器——只输出文字，不能操作文件、不能调 API、不能上网。让 AI 真正”做事”需要三层能力。

4.1 Tool Calling — 函数调用

维度 说明
定义 LLM 返回结构化 JSON 表达”我要调某某工具，参数是这些”，外层程序执行并反馈结果
本质 模型只负责”做决定”（选哪个工具+传什么参数），程序负责”真执行”
一个循环 用户问”上海天气”→ 模型返回 get_weather(location="ShangHai") → 程序调天气 API → 结果还给模型 → 模型用自然语言回答你

LLM 说”我要读文件”，Agent 帮它读。LLM 说”我要调 API”，Agent 帮它调。LLM 自己什么都没做，但它决定了每一步该做什么。

4.2 MCP — 模型上下文协议

最早的实现方式是把每个工具的集成逻辑硬编码在 Agent 主程序里。这导致了著名的 M×N 集成地狱：N 个 AI 模型 × M 个外部工具 = N×M 套定制集成。

维度 说明
定义 Anthropic 2024年11月开源的开放标准协议，让 AI 应用通过统一接口连接外部工具和数据源
三个角色 Host（AI 应用，如 Claude Desktop）→ Client（协议组件，1:1 连接 Server）→ Server（把外部系统能力包装成标准化工具）
三种能力 Tools（可执行操作）、Resources（只读数据）、Prompts（提示模板）
行业地位 2025 年 12 月捐赠给 Linux 基金会 Agentic AI Foundation，OpenAI、Block 等公司随后宣布支持，月下载量 9700 万次

就像 USB-C 统一了充电口——MCP 统一了 AI 工具接口。你不需要为每个模型单独写集成代码，只要实现一个 MCP Server，所有支持 MCP 的 AI 应用都能用。

4.3 Computer Use — 像人一样操作电脑

维度 说明
定义 AI 通过虚拟鼠标和键盘，直接操控电脑屏幕上的应用——打开软件、点击按钮、填写表单
与 Tool Calling 的区别 Tool Calling 是”调 API”（结构化、精确），Computer Use 是”看屏幕+操作 GUI”（视觉驱动、通用）
代表产品 Anthropic Claude Computer Use、OpenAI CUA（Computer Using Agent）
典型场景 操作没有 API 的遗留系统、跨多个应用完成复杂流程

五、沉淀：Skill 技能包

5.1 Skill — 技能包

维度 说明
定义 存放在 SKILL.md 中的 Markdown 指令包，教 Agent 如何完成特定任务
与 Prompt 的区别 Prompt 是”一次性指令”，Skill 是”可复用的流程级指令包”——每次遇到同类任务自动加载
存放位置 项目级 .cursor/skills/ 或个人级 ~/.cursor/skills/

关系：Prompt 是”每次口头教做菜”，Skill 是”写成菜谱贴在厨房”——下次说”做红烧肉”，Agent 自动按菜谱来，不用从头教。

六、自主：Agent 智能体

6.1 Agent — 智能体

维度 说明
核心公式 Agent = Model（智力）+ Harness（手脚+流程）
核心循环 观察 → 规划 → 行动 → 验证 → 重复，直到任务完成
与 LLM 的区别 LLM 是”一问一答的文字处理器”；Agent 是”能自己拆任务、调工具、看结果、再调整的自主系统”

一句话道破本质：Agent 就是所有不需要智能的部分拼在一起，给真正智能的 LLM 打工。 LLM 不会读文件？Agent 帮它读。LLM 不会联网？Agent 帮它搜。LLM 不会执行命令？Agent 帮它跑。

七、落地：Harness、Workflow 与 Workspace Agent

前面的概念让 AI 能”做事”，但要让它在生产环境中可靠运行，还需要三层保障。

7.1 Harness — 执行框架 / 安全外壳

维度 说明
定义 包裹在 LLM 外面的整套软件基础设施，负责 Agent 循环、工具调用、上下文组装、权限审批和用户界面
三大职责 ① 权限控制（7 层纵深防御）② 上下文管理（自动压缩、裁剪、注入）③ 工具调度（并发安全、流式执行）

Harness 的安全哲学：

原则 含义
否决优先（Deny-First） 宁可错误阻止一个安全操作，绝不错误放行一个危险操作
渐进信任（Graduated Trust） 每次新会话，信任从零开始重建——Agent 一开始什么都不能做
纵深防御（Defense in Depth） 7 层独立防线，任何一层都能拦截——从全局禁止列表到高风险显式确认

Harness 是”把 LLM 包装成可靠 Agent”的系统工程。Claude Code 的源码中，核心 Agent 循环只占 5%，剩下 95% 全在解决”循环跑起来之后怎么保证不跑偏”。

7.2 Workflow — 工作流

维度 说明
定义 把多步骤任务编排成可重复、有顺序的流程
与 Agent 的区别 Agent 是”自主从零规划每一步”；Workflow 是”步骤和分支相对固定，但每步可调用 LLM/工具”
典型场景 文档更新：提案 → 人工 Review → 按任务清单实施 → 跑 CI → 归档

Workflow 是”标准化流水线”——你知道要做什么，只是用 AI 来加速每一步。Agent 是”自主探索”——你不知道具体怎么走，但告诉 AI 目标，让它自己找路。

7.3 Workspace Agent — 长期数字员工

维度 说明
定义 能持续运行、跨会话保持上下文、拥有持久记忆和工作空间的 Agent
与普通 Agent 的区别 普通 Agent 是”一次性临时工”（会话结束就失忆）；Workspace Agent 是”长期员工”（记住你的偏好、项目上下文、历史决策）
代表 OpenAI Workspace Agents、团队共享智能体
关键能力 持久记忆 + 权限体系 + 团队协作 + 持续学习

八、总结：AI 进化全景图

一句话总结：AI 的进化，就是从”给你一段文字”到”帮你把事办成”的旅程。Token 和 Context Window 是基础限制，Prompt 和 Context Engineering 让 AI 听懂你，RAG 让 AI 不再瞎编，Tool Calling / MCP / Computer Use 给 AI 装上了手脚，Skill 沉淀了重复流程，Agent 让 AI 能自主执行，Harness / Workflow / Workspace Agent 让它能安全、可靠、持续地落地干活。
