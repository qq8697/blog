1 个故事讲清楚系统架构

2019-12-12
技术 系统架构
缓存 Redis 数据库 分库分表 读写分离 CDN Elasticsearch 微服务 RPC 消息队列 Docker Kubernetes 云原生 负载均衡 服务治理

一、前言：你以为的”高大上”，都是被问题逼出来的

很多刚接触系统架构的人，会有一种错觉：

大厂系统之所以复杂，是因为他们一开始就设计了一套复杂架构。

于是我们看到 Kubernetes、微服务、分布式数据库、消息队列、云原生……这些名词组合起来，好像代表着”高级架构”。

但真实世界里的架构演进，并不是这样的。没有哪个团队一开始立项，就坐下来设计：

“未来我们需要 500 个微服务，需要 Kubernetes 集群，需要服务治理体系。”

真实情况往往是：凌晨两点，服务器报警，数据库 CPU 100%，用户投诉 —— “为什么支付成功了，订单还显示处理中？”开发人员打开电脑：”看来，我们又需要改架构了。”

架构不是设计出来的，而是被问题逼出来的

一个系统的发展过程，通常是这样的：

每一层架构，与其说是追求技术先进，不如说是为了解决当时最痛的问题。

本文通过一个电商项目，完整走一遍系统架构的演进过程。项目名字叫淘淘商城，它经历了：

看看那些看起来复杂的架构技术，到底是如何一步一步出现的。

需要注意的是，真实企业不会严格按照这条路线演进，不同公司的技术选择取决于业务规模、团队能力和历史包袱。本文展示的是一种典型的互联网系统演进路径。

二、故事开始：小团队做了一家电商网站

故事发生在某一天。领导要求你和两个同事做一个电商网站。功能很简单：用户注册登录、浏览商品、添加购物车、提交订单、在线支付。

第一版系统非常简单：

所有东西全部放在一台服务器：页面代码、后端程序、数据库、图片文件。

阶段 1：单机架构

这个阶段最大的目标不是性能，而是：**快速验证产品是否有人使用。**技术非常简单：

也就是经典的 LAMP：

名称 含义
L Linux
A Apache
M MySQL
P PHP

当然，现在也可能使用 Java Spring Boot、Node.js、Go，但思想一样：一个应用，一个数据库，一台服务器。

很多人认为”单机架构太简单，不算架构。”这是错误的。优秀架构的第一原则：

当前阶段够用，就是好架构。

如果每天只有几百个用户，部署 Kubernetes、微服务、消息队列、分布式数据库，不是先进，而是在制造复杂度。

单机架构的问题

随着用户增长，每天 100 个用户变成 10000 个用户，服务器开始出现问题：CPU 100%、内存不足、磁盘 IO 很高。

原因在于应用程序和数据库抢同一台机器资源。用户访问商品时，应用需要 CPU 进行计算，数据库也需要 CPU 进行查询，两个系统互相影响。于是第一次架构升级出现。

阶段 2：应用与数据分离

问题：应用和数据库抢资源

解决方案：拆成两台服务器。

应用负责接收请求和业务计算，数据库负责数据存储和查询，两者职责分开。应用和数据库拆分后，两者拥有独立的 CPU、内存和磁盘资源，不再互相争抢，同时也为后续独立扩展创造了条件。

单点故障（SPOF）

但这里出现一个新问题——数据库仍然是单点故障。SPOF（Single Point of Failure）的意思是：一个组件出现故障，整个系统不可用。例如数据库挂了，虽然应用服务器还活着，但没有数据库，业务无法运行。

下一步，我们需要解决单台服务器性能不足的问题。

阶段 3：应用服务器集群

问题：一台应用服务器扛不住了

淘淘商城第一次搞双十一促销，活动开始 10 分钟，50 万人涌入首页。突然 10 万用户同时访问商品页面，应用服务器 CPU 直接 100%。

最直接的方法是买更大的机器，这叫垂直扩展（Scale Up）——从 8 核 CPU 升到 32 核、64 核。但机器性能存在上限，不可能无限增加。

水平扩展（Scale Out）

于是出现另一种思路：增加机器数量。

负载均衡（Load Balancer）

负载均衡的作用是把用户请求分发给不同服务器：

常见技术有 Nginx、HAProxy、LVS、云负载均衡等。

Session 共享问题

集群化后出现一个重要问题。假设用户登录时请求被分到应用服务器 A，Session（保存用户 ID、登录状态、购物车信息的凭证）存在 A 上。第二次访问时负载均衡把请求分到了 B，但 B 不知道用户已经登录，因为 Session 在 A。

方法 1：Session 复制

服务器之间互相同步 Session。问题是服务器越多，同步成本越高。

方法 3：无状态设计（Stateless）

这是更重要的架构思想——服务本身不保存用户状态。不用 Session，改成 Token：用户登录后服务器生成 Token，客户端保存 Token，以后每次请求携带 Token，任何服务器都可以处理请求。（Session是“服务端记住你”，Token是“你自己证明你是谁”。）

一个服务越无状态，就越容易水平扩展。这也是后来微服务、云原生大量采用这种思想的原因。后面我们会看到，Kubernetes 中服务的自动扩缩容，本质上就依赖服务尽可能无状态——如果某个实例保存了用户状态，实例的增减都会变得复杂。

阶段 4：数据库缓存

问题：数据库快撑不住了

双十一当天，首页爆款商品被用户疯狂刷新，数据库查询量飙升到每秒 10 万次。经过前几个阶段，系统已经变成：

应用服务器已经可以水平扩展，但新的瓶颈出现了——数据库压力越来越大。

为什么数据库容易成为瓶颈？

数据库承担了太多事情。例如用户打开商品详情页，一个热门商品可能一天被访问 100 万次，但商品信息可能几个小时都不会变化（商品名称、价格、库存等）。这些数据大量用户重复读取，如果每次都查询数据库，数据库压力巨大。

缓存（Cache）

缓存的核心思想是：把经常访问的数据，提前放到一个更快的位置。

以前用户请求需要经过应用再到 MySQL 返回商品信息，现在加了 Redis 缓存后，应用先查缓存，有数据直接返回，没数据再查数据库并写入缓存。这个流程叫 Cache Aside Pattern（旁路缓存模式）：

缓存速度更快的原因在于：Redis 直接操作内存数据结构，避免了大量磁盘 IO 和复杂的查询优化过程，因此在简单 KV 访问场景下通常具有更低的延迟。

常见缓存技术：

类型 技术
浏览器缓存 HTTP Cache
CDN缓存 CDN
本地缓存 Caffeine
分布式缓存 Redis

实际生产环境通常采用多级缓存，而不是单独依赖 Redis。一次请求可能依次经过：浏览器缓存 → CDN 缓存 → Nginx 缓存 → 本地缓存（Caffeine） → 分布式缓存（Redis） → 数据库。每一层都在尝试拦截请求，减少对下一层的压力。

缓存带来的新问题

缓存不是简单加一个 Redis 就结束，真实系统会遇到以下问题：

缓存穿透（Cache Penetration）：查询一个不存在的数据，例如攻击者不断请求 商品ID = 999999999，Redis 没有、MySQL 也没有，每次请求都直接打到数据库。解决方式有两种：一是缓存空值（Redis 保存 NULL，下次直接返回），二是使用**布隆过滤器（Bloom Filter）**提前判断数据是否可能存在，不存在直接拒绝。

缓存击穿（Cache Breakdown）：某个热点数据突然过期，例如 iPhone X 的缓存在 10:00 过期，100 万用户同时访问，发现缓存不存在，同时访问数据库，数据库瞬间压力巨大。解决方式包括：热点数据永不过期、加锁控制、异步更新缓存。

缓存雪崩（Cache Avalanche）：大量缓存同时失效，例如所有商品缓存 30 分钟过期，到时间点后大量请求同时进入数据库导致崩溃。解决方式是缓存过期时间增加随机值（如 30 分钟 + 随机几分钟），让失效时间分散。

阶段 5：数据库读写分离

数据库读写分离

虽然缓存解决了一部分读压力，但订单数据、支付数据必须写数据库，写入压力仍然存在。

数据库既负责读（查询商品、订单、用户），又负责写（创建订单、支付、修改库存），读写互相影响。解决方案是拆成**主库（Master）**负责写操作，**从库（Slave）**负责读操作：

主从复制与主从延迟

主库数据会复制到从库。例如用户下单后订单写入主库，然后同步到从库。但复制不是瞬间完成的，这就产生了主从延迟（Replication Lag）。

例如 10:00:00 用户支付成功，主库订单状态变为已支付，10:00:01 才复制到从库。如果此时用户刷新订单读取的是从库，可能看到”未支付”。

读写分离的代价：用一定的数据一致性换取更高的读取能力。

电商系统常见策略是：支付成功后立即查询走主库，普通商品浏览走从库。

阶段 6：分库分表

问题：数据越来越多，单个数据库装不下了

几年之后，淘淘商城数据增长，订单表从 100 万条变成 10 亿条，查询越来越慢，数据库磁盘越来越大，备份越来越慢。继续买更大的数据库服务器（垂直扩展）也有极限，于是进入分库分表。

分库分表的核心思想是：把原来一个巨大的数据库，拆成多个更小的数据库和数据表。

垂直分库

按照业务拆分。以前一个数据库包含用户表、商品表、订单表、支付表、库存表，拆成：

好处是不同业务压力隔离，商品查询很多不会影响支付系统。

水平分表

垂直分库解决了业务隔离，但单张表仍然可能太大（如 10 亿订单）。水平分表是把一张大表拆成多张结构相同的小表：

分片键（Sharding Key）

拆分需要依据一个规则，这就是分片键。例如按照 user_id 分片，规则是 user_id % 4：

  • 用户 10001：10001 % 4 = 1，保存到 order_1
  • 用户 10002：10002 % 4 = 2，保存到 order_2

分库分表带来的新问题

分库分表解决了性能问题，但带来了新的复杂度。以前一个 SQL 就能查到的数据，现在不知道数据在哪个表，可能需要查询所有分片。

跨库 Join：以前 订单表 join 用户表 很简单，现在两个表可能不在一个数据库。

分布式事务：下订单需要订单数据库、库存数据库、支付数据库三个数据库同时成功，如何保证一致性？这就是分布式事务问题。

数据倾斜（Data Skew）：按照用户 ID 分片，但某些大客户订单特别多，导致某个分片数据量远超其他分片（如 order_0 100 万、order_1 100 万、order_2 10 亿）。这种情况也叫”热点分片”——某个分片因为大客户（如大卖家）的存在而承载了远超其他分片的数据和流量。

应用原本执行 select * from order，现在需要经过：SQL 解析 → 计算分片规则 → 定位目标数据库 → 合并结果。这个过程叫 SQL 路由，是分片中间件的核心能力。

常见工具有 Apache ShardingSphere、MyCat，它们提供分片规则管理和 SQL 路由能力。

阶段 7：CDN 与反向代理

问题：用户遍布全国，访问延迟不同

随着业务增长，新的需求出现。

CDN（Content Delivery Network）

CDN 即内容分发网络。以前服务器在北京，上海、广州、成都、深圳的用户访问距离不同，导致延迟不同。CDN 把内容提前复制到边缘节点，用户访问附近的 CDN 节点获取图片等静态资源，速度大幅提升。

CDN 适合缓存图片、CSS、JS、视频、下载文件等静态资源。

反向代理（Reverse Proxy）

CDN 后面通常还有反向代理（如 Nginx），客户端不知道真实服务器：

反向代理可以提供：

  • SSL 卸载：HTTPS 加密由 Nginx 完成，而不是每个应用处理
  • 请求转发：/api/user 转发到用户服务，/api/order 转发到订单服务
  • 安全防护：限制异常请求、隐藏内部服务器

阶段 8：搜索引擎与专业存储

问题：商品搜索和多模型存储

Elasticsearch 搜索引擎

商品搜索越来越复杂。以前 MySQL 用 like '%手机%' 查询，数据少没问题，但商品达到千万级时，用户搜索”苹果 手机 256G 黑色”，关系数据库并不是为海量全文检索场景设计的。

Elasticsearch 基于**倒排索引（Inverted Index）**实现近乎实时的全文检索。普通数据库像查字典逐条查找，倒排索引像字典目录——先查关键词，再找到对应商品 ID：

搜索速度大幅提升。

多模型存储

系统越来越复杂，不同数据有不同需求：用户行为（浏览记录、点击记录）适合文档存储，订单需要强一致事务，日志需要海量写入。不可能全部放 MySQL，于是出现多模型存储：

场景 技术
订单交易 MySQL
缓存 Redis
搜索 Elasticsearch
文档数据 MongoDB
海量日志 大数据平台

不是某个数据库不够强，而是不同问题需要不同工具。

到这里，淘淘商城已经从一台服务器演进到应用集群、缓存、数据库集群、分库分表、CDN + 搜索 + 多存储。但新的问题出现——代码越来越难维护。

阶段 9：服务化、微服务与微服务治理

问题：代码越来越难维护

经过前面的演进，淘淘商城已经不是一个简单的网站，系统里面有用户系统、商品系统、订单系统、库存系统、支付系统、物流系统、营销系统。但最开始所有代码都写在一个项目里面，这就是单体应用（Monolithic Application）。

什么是单体应用？

一个应用包含了所有业务功能，一个代码仓库、一个工程、一个部署包：

启动时一个命令 java -jar taotao-shop.jar 即可运行整个系统。

单体应用的早期优势

很多优秀系统最初都是单体，原因是简单：开发简单（所有代码在一起，调用是直接方法调用）、部署简单（一个包直接发布）、调试简单（一个项目里面排查）。

单体应用的三个痛点

随着业务增长，问题开始出现：

代码越来越复杂：几年后项目 100 万行代码、100 个开发人员，修改商品功能可能影响订单，修改支付可能影响库存。

发布越来越困难：只修改优惠券模块，但必须重新编译、重新打包、重新部署整个应用。

无法独立扩容：双十一期间商品浏览 100 倍增长，但订单系统压力正常，单体应用只能整体扩容（原来 2 台增加 20 台），真正需要扩容的是商品模块，造成资源浪费。

服务化（SOA）与微服务架构

SOA（Service Oriented Architecture） 是大型企业早期的服务化思想，强调将业务拆分为可复用的服务，通常依赖 ESB（企业服务总线）进行通信。微服务是 SOA 的进一步演进，更强调：小粒度、自治、独立部署、去中心化——每个服务可以有自己的数据库和技术栈，服务之间通过轻量级协议通信。不过 SOA 并未被淘汰，在企业内部系统集成（如银行、保险等行业的 ESB 场景）中仍然广泛使用，微服务则更偏向互联网高并发场景下的轻量级服务化。

新的思想出现——按业务能力拆成多个独立服务：

每个服务独立开发、独立部署、独立扩容。例如商品访问量巨大时，只增加商品服务实例，而不是扩容整个商城。这就是微服务架构（Microservices Architecture）。

RPC（Remote Procedure Call）

服务拆开后，订单服务调用库存服务，两个服务可能在不同机器，怎么办？RPC（远程过程调用）让你像调用本地方法一样调用远程服务器上的方法：

常见 RPC 框架有 Dubbo、gRPC、Spring Cloud OpenFeign。初学者可能会问：为什么不用 HTTP？微服务内部调用通常采用 RPC 框架，因为 RPC 可以提供服务治理、接口定义、高效序列化等能力。当然，HTTP/REST 在对外开放的接口场景中仍然大量使用。

服务发现（Service Discovery）与注册中心

服务越来越多，库存服务可能有多个实例（192.168.1.10、192.168.1.11、192.168.1.12），订单服务怎么知道调用哪个地址？

服务发现引入注册中心（如 Nacos）。服务启动时主动注册地址，调用方查询注册中心获取可用实例列表：

常见注册中心有 Nacos、Eureka、Zookeeper、Consul。

此外，微服务拆分后带来的分布式事务问题，也有成熟的解决思路：Saga 模式将大事务拆分为多个本地事务，每一步都有对应的补偿操作；TCC（Try-Confirm-Cancel） 通过预留资源的方式保证最终一致性；阿里开源的 Seata 框架则提供了开箱即用的分布式事务解决方案。

配置中心（Configuration Center）

服务越来越多后，每个服务都有数据库地址、开关配置、服务参数等配置项，逐个管理非常低效。配置中心统一管理所有服务的配置，修改配置无需重新部署。例如 Nacos 可以同时承担注册中心和配置中心两个角色。

微服务数量继续增长（100 个服务、500 个实例），新的治理问题出现。

熔断（Circuit Breaker）

服务挂了怎么办？订单服务调用库存服务，库存服务故障，如果所有请求继续调用可能导致整个系统雪崩。熔断类似电路保险丝，当某个服务持续失败时暂时停止调用，返回默认结果（如购物车显示库存”不确定”，但网站仍然可以访问）。常见技术有 Sentinel、Hystrix。

降级（Fallback）

系统压力过大时关闭非核心功能。电商系统核心功能是登录、下单、支付，非核心是”猜你喜欢”、商品推荐。压力过大时关闭推荐，保证交易流程。

限流（Rate Limit）

限制请求数量，例如支付接口每秒最多 10000 请求，超过则排队或拒绝。

全链路追踪（Distributed Tracing）

微服务时代一个请求可能经过几十个服务，出现慢问题时不知道哪个服务慢。链路追踪可以查看一次请求在各服务的耗时：

常见技术有 SkyWalking、Jaeger、Zipkin。

到这里，淘淘商城完成了从单体应用到服务化再到微服务的演进。此时公司已经扩张到 200 名开发人员，一个项目中多人修改频繁产生代码冲突，独立部署和独立扩容成为刚需。但服务越来越多，谁来管理这些服务？100 个服务每个需要安装环境、配置依赖、启动停止、扩容，人工已经无法管理。

阶段 10：消息队列和异步通信

消息队列与异步通信

服务之间调用越来越复杂，一次用户下单需要调用订单服务、库存服务、支付服务、优惠券服务、物流服务，链路越来越长，任何一个服务慢都会影响整个请求。

同步方式下，如果短信服务慢，整个下单变慢。消息队列把流程改成异步：订单服务只负责创建订单，其他事情（扣库存、加积分、发通知）通过消息队列异步处理。这叫异步解耦。

消息队列还有削峰填谷的作用。秒杀活动 10 秒内 100 万请求，如果全部直接访问数据库会崩溃，消息队列像缓冲池，让系统慢慢处理。

消息队列还经常用于实现分布式系统中的最终一致性（Eventual Consistency）。例如订单创建成功后，积分稍后到账——各服务之间不要求强一致，但保证最终数据一致。这在电商系统中非常常见。

常见消息队列有 Kafka、RocketMQ、RabbitMQ。

阶段 11：容器化与自动化交付

问题：我的电脑可以运行，服务器为什么不行？

这是软件开发历史上的经典问题。开发环境 Java 、Tomcat、依赖包、配置文件都正常，但服务器上 Java 版本不同、环境不同、配置不同，启动失败。原因在于应用依赖运行环境。

Docker

Docker 解决了这个问题，核心思想是：把应用和运行环境一起打包。

以前部署需要代码 + 服务器环境 + 各种配置，现在打包成镜像（Image），包含 Java 环境、代码、依赖、配置。运行时成为容器（Container）：

优势是一次构建，到处运行——开发环境、测试环境、生产环境都可以运行。

Kubernetes

但 Docker 只解决单个容器运行问题。如果现在有 1000 个容器，需要自动部署、自动扩容、自动恢复、自动调度，于是进入 Kubernetes。

阶段 12：云原生

问题：机器越来越多，人工运维无法承受

现在系统可能有 1000 个服务实例、100 台服务器，每天可能发生服务挂掉、流量增加、发布升级、机器故障，人工处理已经不现实。

Kubernetes（K8S）

很多人理解 Kubernetes 就是管理 Docker，不完整。更准确地说，Kubernetes 是一个自动化管理容器的控制系统。

你告诉 Kubernetes”订单服务运行 5 个实例”，它负责创建 5 个容器、监控状态、发现挂掉自动重新创建、流量增加自动扩容。这叫声明式管理（Declarative Management）。

传统方式是告诉机器第一步执行命令、第二步启动服务、第三步修改配置。Kubernetes 是告诉系统”我想要什么状态”，例如 replicas: 5 表示要 5 个订单服务实例，至于怎么创建、在哪里运行、失败怎么办，由 Kubernetes 负责。这就是自动化控制。

云原生最终形态

最终淘淘商城架构：

开发人员不再关心哪台机器运行服务、服务挂了怎么办、如何扩容，只需要提交代码，流水线自动完成：代码提交 → 自动测试 → 构建镜像 → 部署 Kubernetes → 上线。这就是云原生（Cloud Native）。

云原生 ≠ 上云

把服务器从机房搬到云服务器，这叫云上部署。真正云原生强调：容器化、自动化、弹性伸缩、服务治理、可观测性、DevOps。

最后的思考：架构演进没有终点

回头看淘淘商城：一台服务器 → 应用集群 → 数据库集群 → 分布式系统 → 微服务 → 容器 → 云原生。

很多人问：”那是不是云原生就是最终答案？”不是。因为未来还会出现新的问题——流量继续增长、业务继续复杂、全球化部署、AI 服务加入系统，新的问题会产生新的架构。

架构的本质是什么？

不是堆技术，不是追求最新名词，而是：

在业务目标、技术成本和系统复杂度之间找到平衡。

真正优秀的架构不是最复杂的架构，而是：

在当前阶段，用最简单的方式解决最大的问题。

所以，不要问”我要不要上微服务？”，应该问”我的问题，是否需要微服务解决？”不要问”我要不要 Kubernetes？”，应该问”我的系统复杂度，是否已经超过人工管理能力？”

也需要警惕过度拆分。团队不到 20 人时，单体应用的开发效率往往更高；过早拆分微服务可能导致”分布式单体”的灾难——服务间耦合严重，每次发布仍需要协调多个服务同时上线。架构演进不是单向的，有时拆分后发现调用链过长，合并回单体反而是更好的选择。

最后送给所有架构学习者几句话：

每一个架构组件，最初都不是为了炫技而存在。它们只是某个团队，在某个深夜，面对一个已经撑不住的问题时，找到的一种解决方案。

架构不是设计出来的，而是在一次次真实挑战中演进出来的，技术演进不是能力增强，而是复杂度转移。
